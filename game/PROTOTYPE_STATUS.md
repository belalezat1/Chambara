# Circular guard and slash controls

- Calibrated phone tilt selects a continuous guard point anywhere inside a circle: tilt direction selects its angle and tilt amount selects its radius. Input is scaled 2×, so the rim needs about half the original physical tilt. Near-neutral input moves to center while retaining the last direction for slash intent; roll alone does not select a new guard.
- The primary grip translates horizontally/vertically with that direction, and the blade points along it. At the top of the circle the grip requests a 50 cm rise and 38 cm shift toward the body from neutral, placing the hands high beside/behind the head while the reach fitter preserves two-arm contact. The lower guard retains its original 14 cm vertical range. The existing contact-aware two-hand IK moves both arms with the weapon; arm reach fitting remains active.
- A cut can begin only when the guard is at least 75% of the circle radius. Acceleration events inside that boundary are ignored and not queued. An accepted cut commits the current guard, crosses the center in 220 ms, holds the opposite endpoint for 100 ms, and blends back to current aim over 280 ms. New cuts are rejected during the animation.
- The phone uses gravity-free acceleration magnitude, a default 12 m/s² threshold, 120 ms quiet arming, and a 650 ms cooldown. The controller page exposes a 5–25 m/s² threshold slider. Devices without acceleration readings can still aim but cannot trigger physical slashes.
- A cumulative slash counter travels with orientation samples; host session/calibration changes establish a new baseline, and stale/disconnected input returns to rest. Existing room pairing remains one phone per host.
- Desktop: select a simulated pose, then Test slash. The circle indicator shows the current procedural sword point and phase. Manual reach buttons are disabled during circle control; body-clip preview buttons remain separate.
- Validation: 66 unit tests; TypeScript and production build checks; browser guard/slash smoke checks with finite IK and zero reported grip error, including the overhead guard. Real-phone sensitivity and physical input signs still require a hardware playtest. Production bundle size warning remains.
- Earlier implementation notes below describe the underlying v05 rig. Circular control replaces direct quaternion/spherical-shell aiming while a calibrated input is live; the shell solver remains for rest/debug poses. Combat, hit detection, and multiplayer match authority are not added.

# Chambara v05 Weapon Solver Status

- Scope: asset-based weapon presentation and two-hand pose solving only. Combat, collisions, hit resolution, AI, rollback, and multiplayer authority remain out of scope.
- Runtime source of truth: `Baizhong_Kendo_Animations_v05.glb` plus `Baizhong_Kendo_Animations_v05_manifest.json`, copied into both `assets/player` and `game/public/assets/player`.
- Loader contract: `WeaponRoot`, `ReachCenter`, `GripPrimary`, `GripSecondary`, `BladeBase`, `BladeTip`, `BladeUp`, `Shinai`, `hand.R`, and `hand.L` are validated at load time. All twelve manifest animation groups are required. The old socket hierarchy is not used and no runtime reparenting is performed.
- Weapon geometry: all grip and blade offsets come from the v05 marker world transforms. Forward is `BladeTip - BladeBase`; up is the orthogonalized `BladeUp - BladeBase`; right completes the marker frame. The visible forward diagnostic is computed from the actual BladeBase/BladeTip nodes.
- Target solve: phone orientation uses the Motion Lab ZXY quaternion, an explicit `inverse(reference) * current` recenter delta, and one proper phone-controller-frame to marker-derived gameplay-frame alignment. The fixed physical correction is `C = RotationAxis(PHONE_RIGHT_EDGE_AXIS, pi)` composed as `B_corrected = B * C`, preserving right-edge rotation while reversing the observed top-edge and screen-normal signs. The physical neutral is screen-up with the top edge toward the monitor; no per-axis pitch repair is applied to real-device or diagonal input. Grip translation remains around the static root-relative ReachCenter on the damped, thick front spherical shell (40% orientation swing blend); roll changes orientation without adding shell swing.
- Reach state: READY .82, BLOCK .65, ATTACK_WINDUP .78, ATTACK_ACTIVE .92, ATTACK_RECOVERY .82, and REACTION .65. State transitions are exponentially damped and exposed through `setReachState()` plus desktop debug buttons. Body clips are a separate `playAnimation()` control, so reach-state changes do not implicitly start or replace animation playback. The current neutral shell is about 35.9 cm; observed neutral/block/active radii are 35.9 / 28.5 / 40.3 cm.
- Arms: upper-arm and forearm lengths are measured from the imported v05 skeleton (about .2526 m + .2302 m, .4827 m maximum on each side). The v04-authored `hand.R`/`hand.L` contact frames are persisted in the v05 manifest and applied as local hand contacts (`GripPrimary`/`GripSecondary`), including rotation offsets. The manifest's `armMeasurements.rightShoulderJointRest` and `.leftShoulderJointRest` values are converted into runtime glTF root space and are the authoritative gameplay anchors; a one-time rest skeleton capture is retained only for validation/debug and as the warned fallback for older manifests. Animation transform nodes still provide presentation input, while the procedural IK chain is synchronized explicitly and detached from the later skeleton-prepare overwrite. Each frame follows animation prepare -> baseline-relative local torso/chest/shoulder follow -> two-link IK, so follow can be toggled without changing the target or accumulating drift; torso follow defaults OFF for physical validation.
- Diagnostics: the inspector reports raw absolute device quaternion, calibration reference, relative quaternion, mapped gameplay delta, fixed frame alignment, final gameplay weapon quaternion, marker-derived blade forward/up, visible forward dot, plus the existing marker validity, geometry, ReachCenter/root/world, state/fraction/shell, arm reach, feasibility/clamping, grip error, hand contacts, shoulder anchors, torso-follow, target, shoulder/pole, shell, and debug-toggle data.
- Verification: `pnpm test` (57 tests), `pnpm run typecheck`, and `pnpm run build` pass. Live HTTP smoke on the dev server returns 200 for `/`, `/controller?room=ABC123`, and the v05 manifest with all 12 actions. A real browser smoke pass was not available in this session because the CUA environment exposed no browser provider. Physical Android retest remains the final validation for the corrected left/right and roll signs. Extreme swings may intentionally report a reduced shell radius or IK clamp while preserving finite output.
- Known limitations: the relay remains development-only, real DeviceOrientation still needs HTTPS and a physical Android permission check, and the local dev page may log a harmless favicon or relay warning.
